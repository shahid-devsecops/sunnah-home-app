 Executive Summary

  The current root cause is a combination of stale persisted selection + missing auth/member link + heuristic fallback architecture.

  Usman can still be selected after Shahid logs in because the app has no authoritative auth.user.id -> FamilyMember.id mapping anywhere in the codebase. Instead, the authenticated default is inferred from profile.name and family roles, while useSelectedMember()
  gives any persisted selected_member_id precedence over that inferred default. Since selected_member_id is also synced through the generic user_data store, a stale child selection can be rehydrated on sign-in and override the intended “ME” default.

  The newer member-scoped storage work is only partial. The Home Today surface uses member-scoped hooks for some personal domains, but major personal routes and modules still read/write global keys directly: Salah, Hifz, Fasting, habits, health, check-ins, journal,
  workouts, reminders, and insights. That means child and household privacy is not architecturally safe yet across the full app.

  Auth → FamilyMember Mapping

  1. Is there an authoritative auth.user.id -> FamilyMember.id relationship?

  No.

  2. Where is it stored?

  Nowhere in the current app model. FamilyMember has only id, name, role, age, color, avatar, chores.

  3. Where is it created?

  Nowhere. Onboarding creates a family member by matching/creating from profile.name, not auth identity.

  4. Where is it hydrated?

  It is not hydrated because it does not exist.

  5. Where is it consumed?

  Not consumed anywhere; the app instead consumes profile.name and family roles.

  6. Can the system fall back to heuristics?

  Yes, entirely.

  7. Can those heuristics select the wrong child?

  Indirectly yes, and architecturally yes. The primary resolver tries hard not to choose a child, but the overall system can still land on a child via stale persisted selection. Also the identity model itself is heuristic:

  Initialization Order / Race Analysis

  Order on home load:

  1. React mounts HomePage
  2. useFamilyMigration() runs
  3. useStore() hooks begin with in-memory fallbacks, then hydrate from localStorage in effects
  4. Supabase onAuthStateChange can call syncFromCloud()
  5. syncFromCloud() mutates localStorage and emits updates
  6. useSelectedMember() recalculates from selectedId, family, profile

  This means there is a real overwrite path:
  • initial render may have no selectedId
  • fallback resolves to primaryMember
  • later cloud sync hydrates stale selected_member_id = mem_usman
  • useSelectedMember() then switches active member to Usman

  So yes, initialization order contributes. It is not the only bug, but it makes the stale persisted selection authoritative after auth hydration.

  LocalStorage Analysis

  veedu:selected_member_id semantics are currently account-scoped only because it is mirrored into generic user_data, but the implementation is leaky and incomplete.

  Observed behavior:
  • read via useStore("selected_member_id", undefined)
  • local reset removes the local key
  • explicit household is persisted as "household"
  • explicit child selection persists as that child id
  • cloud sync can restore a prior value on sign-in

  Important detail: logout only clears local state. There is no explicit remote delete path for selected_member_id; only a generic upsert with value: undefined. Because syncFromCloud() only merges server rows into local and never deletes absent/stale rows, stale
  selection can survive server-side and return on next login.

  So the semantics are not safely “logout clears selection”. They are closer to:
  • local device value with cloud rehydration
  • no reliable deletion contract
  • persisted explicit selection can override post-login default

  Critical Findings

  • CRITICAL: There is no authoritative auth.user.id -> FamilyMember.id link.
  • CRITICAL: useSelectedMember() treats persisted selection as authoritative over authenticated default.
  • CRITICAL: selected_member_id is synced through generic cloud storage and can be rehydrated after login.
  • CRITICAL: logout clears local selection, but remote stale selection is not reliably deleted.
  • CRITICAL: many personal routes still use global personal stores and ignore selected member.
  • IMPORTANT: getPrimaryFamilyMember() is heuristic identity resolution, not canonical identity.
  • IMPORTANT: task creation defaults to current perspective, so wrong perspective causes wrong ownership immediately.
  • POSITIVE: Home Today member-scoped storage integration is directionally correct.
  • POSITIVE: Today suppresses personal data in household mode and suppresses budget for child mode.

  Recommended Fix

  Minimal correct architectural fix:

  1. Introduce an authoritative identity link:

     auth.user.id -> FamilyMember.id
     stored explicitly, not inferred from profile.name.

  2. Change useSelectedMember() semantics:
    • explicit persisted selection may override only after it is validated against the currently authenticated user/session and current family
    • first authenticated load must default to authenticated member
    • logout must fully clear persisted selection for that account/session

  3. Stop syncing selected_member_id as generic long-lived user data unless its semantics are explicitly account-safe and deletable. At minimum, it needs:
    • deterministic delete behavior
    • per-user/per-household validation
    • no blind rehydrate over initial ME default

  4. Finish member scoping for all personal domains, not just Home Today.

  Recommended Fix Order

  1. Add canonical auth/member mapping.
  2. Fix selection persistence semantics and stale cloud rehydration.
  3. Update task creation default semantics after selection is correct.
  4. Complete member-scoped migration for Deen, Me, Review, trends, reminders.
  5. Then continue Wave H2.5 household/Supabase work.

  Things NOT To Change

  • Do not keep patching getPrimaryFamilyMember() heuristics as if that solves authenticated identity.
  • Do not add more name-based fallbacks.
  • Do not keep layering special cases around Usman or “first admin”.
  • Do not continue shipping new UX on top of partially global personal stores.
  • Do not assume passing current unit tests means the auth/member architecture is sound.
