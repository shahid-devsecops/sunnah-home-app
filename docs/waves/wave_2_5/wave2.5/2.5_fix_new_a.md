# FIRDAUS H2.5-A — CANONICAL AUTH → FAMILY MEMBER IDENTITY

Repository:
~/firdous/veedu-home-soul

An independent forensic architecture review found:

CRITICAL:
There is no authoritative auth.user.id → FamilyMember.id relationship.

CRITICAL:
selected_member_id can be restored through generic user_data sync and override
the authenticated user's intended perspective.

CRITICAL:
Task creation defaults assignedTo from the active perspective, so a stale
child perspective causes tasks to be assigned to the child.

IMPORTANT:
getPrimaryFamilyMember() relies on name/role heuristics and must not remain
the canonical authenticated identity resolver.

DO NOT implement Supabase household sharing yet.
DO NOT implement invitations.
DO NOT implement RLS.
DO NOT implement multi-device household collaboration.
DO NOT redesign UI.

This task establishes the canonical account-to-member identity only.

==================================================
1. EXTEND FAMILY MEMBER IDENTITY
==================================================

Inspect the existing FamilyMember type.

Add the smallest backward-compatible field needed:

linkedUserId?: string

Semantics:

linkedUserId === Supabase auth.users.id
→ this FamilyMember represents that authenticated person.

Children and unlinked household profiles:
linkedUserId === undefined

Do NOT use name as identity.

Do NOT use array position.

Do NOT use role as identity.

==================================================
2. CANONICAL RESOLVER
==================================================

Create one authoritative pure resolver:

getAuthenticatedFamilyMember(
  family: FamilyMember[],
  authUserId?: string | null
): FamilyMember | undefined

Rules:

1. Exact linkedUserId match → return member.
2. No auth user → undefined.
3. If no linked match:
   DO NOT randomly choose a member.

For existing legacy data only, define a deterministic migration helper that
can establish the link ONCE if there is exactly one safe candidate.

Do not use getPrimaryFamilyMember() as the runtime identity resolver.

==================================================
3. MIGRATION OF EXISTING USER
==================================================

Existing users currently have no linkedUserId.

For the authenticated user:

Determine the safest existing-member migration strategy.

Preferred:

If exactly one obvious owner candidate exists:
- establish linkedUserId = auth.user.id
- preserve FamilyMember.id

Possible evidence:
- existing onboarding-created primary member
- profile identity
- canonical adult/admin role

But:

If ambiguous:
- do NOT guess
- leave unlinked
- fall back safely to Household
- record the ambiguity for manual resolution

Never link Usman merely because he is the first member.

Migration must be idempotent.

==================================================
4. AUTH INITIALIZATION
==================================================

Trace existing auth/session hydration.

After:

auth session
+
family data

are both available:

resolve authenticated FamilyMember from auth.user.id.

This becomes the only canonical "ME" identity.

Do not select a perspective before the authenticated identity is known.

Avoid race conditions where:

initial render
→ undefined/heuristic member
→ stale cloud selected_member_id
→ child member

==================================================
5. SELECTED MEMBER SEMANTICS
==================================================

Define:

selectedMemberId = authenticated member ID
→ "ME"

selectedMemberId = undefined
→ "HOUSEHOLD"

selectedMemberId = other member ID
→ "OTHER MEMBER"

Do not overload undefined to mean both:
- "auth identity not loaded"
- "Household"

Introduce an explicit initialization/loading distinction if necessary.

For example:

identityLoading = true
identityLoading = false

Then:

after identity resolves:
  authenticated member → selectedMemberId = own member
  no linked member → selectedMemberId = undefined / Household

==================================================
6. PERSISTED SELECTION
==================================================

The existing selected_member_id persistence is unsafe.

Determine whether it should remain persisted.

For now:

- First authenticated load → authenticated user's own member.
- Explicit user selection may persist.
- Persisted selection must be validated against the current authenticated
  user's household/family.
- Never allow a stale selection from another account to become active.

Do NOT treat a persisted child member as authoritative before auth identity
is resolved.

==================================================
7. LOGOUT
==================================================

On logout:

- clear selectedMemberId
- remove local selection
- ensure no stale member perspective is rehydrated for the next user

Do not rely on writing undefined into user_data.

The deletion behavior must be deterministic.

==================================================

- reject invalid/stale member IDs
- do not rehydrate a child selection before identity initialization
- ensure logout cannot leave a previous user's member context

Document the remaining sync limitation for the later H2.5 sync work.
